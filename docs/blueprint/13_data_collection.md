# 13 — Field Data Collection & Seed Pipeline (Phase 0)

Spec references: §Phase 0 (two-scout verification, ODK/Kobo, data model), §4.5 (lifecycle), business plan §5.2.2 (cost-efficient collection). Tables: doc 02 §4, §14.

## 1. Scout protocol (`data-collection/PROTOCOL.md`)

- Two independent scouts per corridor, on different days, without sharing notes. A third scout resolves discrepancies > tolerance.
- Per **park**: name (as locals say it) + aliases, GPS fix (≥ 30 s averaging, accuracy ≤ 10 m), photo of signage/landmark (optional), modes present, typical loading time by mode, operating hours.
- Per **route** (per mode): origin park, destination park, ordered stages with GPS fix + local name, GPX trace of one full ride, fare from each stage to the end (as drivers quote it), any known through-fares for common pairs, frequency estimate (vehicles/hour at peak & off-peak), typical wait.
- Fares recorded as *quoted standard* prices, not what the scout paid after haggling; note haggle range separately.
- Scouts are paid per verified entity; payment triggers on `reconciled`, not on submission (aligns incentives with accuracy).

## 2. ODK/Kobo forms (`data-collection/forms/*.xlsx`)

`along_park_v1`: `park_name`, `aliases` (repeat), `location` (geopoint), `modes` (select_multiple from `mode_config` choices exported), `hours_from/to`, `photo`, `notes`, `scout_id`, `corridor_id` (from a choices list synced from `corridors`).

`along_route_v1`: `corridor_id`, `mode`, `origin_park` (select from parks list or `new_park` group), `destination_park`, repeat group `stage` {`stage_name`, `location`, `is_official_park`, `price_to_end`, `price_currency`}, `through_fares` repeat {`from_stage_seq`, `to_stage_seq`, `fare`}, `frequency_peak_per_hour`, `frequency_offpeak_per_hour`, `typical_wait_min`, `gpx` (file), `notes`.

Both forms carry `form_version`, device id, submission timestamp. Choice lists are generated by `data-collection/scripts/export_choices.ts` from the DB so ids line up.

## 3. Ingestion (`data-collection/scripts/ingest.ts`)

1. Pull submissions via ODK Central/Kobo API → insert `field_submissions` (raw `payload`, `gpx` to storage `field/{city}/{submission}.gpx`).
2. Derive `entity_key` deterministically: park → `park:{city}:{slug(name)}`; route → `route:{city}:{origin_slug}-{dest_slug}:{mode}`; stage → `{route_key}:stage:{seq}`; fares → `{route_key}:fare:{from}-{to}`.
3. Upsert `field_reconciliations` per key: first submission → `awaiting_second`; second → compute variance: location (m), fare (%), stage count diff, name similarity (trigram). Within tolerance (`cfg.field.location_tol_m` 50, `cfg.field.fare_tol_pct` 0.15) → `matched`; else `discrepant` (queue in A-07, request third scout).
4. `admin_publish_field_entity` writes graph rows with `source_type='field_agent'`, `verification_status='field_verified'`, `confidence_score=0.95`, linking `data_sources.field_submission_id`; route `path` from the GPX (simplified with `ST_Simplify` 5 m); `route_legs.distance_m` from path; `in_vehicle_time_estimate_s` from GPX timestamps; `transfer_points` where two routes share a park.

## 4. Seed formats (A-08 CSV drop)

`parks.csv`: `name,aliases|pipe|separated,lat,lng,modes|pipe`
`routes.csv`: `origin_park,destination_park,mode,name`
`stages.csv`: `route_name,sequence,stage_name,lat,lng,is_official_park`
`leg_fares.csv`: `route_name,from_seq,to_seq,fare`
`through_fares.csv`: `route_name,from_seq,to_seq,fare`
Import runs a dry-run diff, then applies with `source_type='import'` and `verification_status` = `candidate` unless a matching `field_reconciliations.matched` exists.

## 5. Abuja pilot corridors (business plan §7, Phase 0 gate ≥ 3)
1. Lugbe ↔ Area 1 / Berger (car + keke feeders)
2. Nyanya/Mararaba ↔ AYA ↔ CBD (minibus + car)
3. Kubwa ↔ Wuse (car + keke)
Backbone parks: Lugbe Park, Area 1 Park, Berger Junction, Nyanya Park, AYA, Kubwa Bus Stop, Wuse Market, Jabi Park (transfer). Field team: 4 scouts, 3 weeks; expected ~120 stages, ~300 leg fares.
